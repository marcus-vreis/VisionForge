## 1. Goal

Cada tarefa concluída pelo time da Spec A vira PR contra `development` no GitHub remoto. CI verde (pytest, ruff, mypy, codespell, coverage 70%, SonarCloud) + aprovação do reviewer-bot são gates obrigatórios pro merge. Branch `main` nunca é tocada por agentes — promotion `development → main` é manual sua.

## 2. Scope

**In scope:**
- Criar/garantir branch remota `development`
- Branch protection rules em `development`
- Fluxo automatizado: worktree → push → PR draft → CI → reviewer-bot → ready → squash merge
- Granularidade 1 PR por tarefa
- Conflict handling (rebase automático em série)
- Lead startup hook valida `gh auth`

**Out of scope:**
- Promotion `development → main` (manual)
- Hotfix flow / release branches
- Release tags (cd.yml já faz em tags `v*.*.*` manuais)
- Notificação fora do repo (Slack, email)
- Cross-repo coordination

## 3. Granularidade e estratégia

| Decisão | Valor |
|---|---|
| Granularidade de PR | 1 PR por tarefa do TASKS.md |
| Branch base | `development` |
| Branch source | `worktree-<auto-name>` (criada pelo Spec A) |
| Merge strategy | `--squash` |
| Conflict strategy | Serializado: 1 merge por vez. Próximo rebase em `development` antes de tentar merge |
| Aprovador no PR | Mesma instância `rv-1` da Spec A — usa `gh pr review --approve` |
| Quem chama merge | Lead via `gh pr merge --squash --delete-branch --auto` |
| Commit message | Conventional Commits (`feat:`, `fix:`, `test:`, `docs:`, `refactor:`) |
| PR title | Primeira linha do commit |

## 4. Branch protection em `development`

Configurada uma vez via `gh api`:

```bash
gh api -X PUT repos/:owner/:repo/branches/development/protection \
  -f required_status_checks.strict=true \
  -f required_status_checks.contexts[]='pre-commit' \
  -f required_status_checks.contexts[]='main' \
  -f required_status_checks.contexts[]='tests' \
  -f required_status_checks.contexts[]='sonarqube' \
  -f required_pull_request_reviews.required_approving_review_count=1 \
  -f enforce_admins=false \
  -f restrictions=null
```

`enforce_admins=false` permite que você (admin) faça override em emergência. Reviewer-bot conta como o 1 approval requerido.

## 5. Fluxo end-to-end

```
[Spec A]: teammate marca task completed, hook gate passa, reviewer approve no plano
  ↓
Lead: cd <worktree-path>
  ↓
Lead: git add -A && git commit -m "<conventional>"
  ↓
Lead: git push -u origin worktree-<name>
  ↓
Lead: gh pr create \
        --base development \
        --draft \
        --title "<first line of commit>" \
        --body "$(cat <<EOF
## Task
Item: <task description from TASKS.md>

## Files changed
$(git diff --name-only origin/development...HEAD)

## Local gate (Spec A)
- pytest: passed
- ruff check: passed
- ruff format: passed

🤖 Generated by VisionForge agent team
EOF
)"
  ↓
Lead: gh pr ready <pr-number>     # tira de draft, dispara CI completo
  ↓
Lead: gh pr checks <pr-number> --watch --interval 30 --required
  ↓                                              ↓
CI fail → lead manda mensagem pro                CI pass → lead pede pra rv-1:
teammate com erros, retry loop (max 3)             "Final review on PR #<n>. Read the diff,
                                                   then `gh pr review <n> --approve` if good,
                                                   `--request-changes` if not."
                                                   ↓
                                                   rv-1 approve → lead: gh pr merge <n> --squash --delete-branch --auto
                                                   ↓
                                                   merge concluído → lead: git checkout development && git pull
                                                   ↓
                                                   lead remove worktree: git worktree remove <path>
                                                   ↓
                                                   lead marca [x] em TASKS.md (commit direto em development)
```

## 7. Script: `lead-startup.sh`

```bash
#!/usr/bin/env bash
set -uo pipefail

# Verifica autenticação gh
if ! gh auth status >/dev/null 2>&1; then
  echo "ERROR: gh CLI not authenticated. Run 'gh auth login' first." >&2
  exit 2  # Bloqueia a sessão
fi

# Garante que development existe (local + remota)
if ! git show-ref --quiet refs/heads/development; then
  git fetch origin development:development 2>/dev/null || \
    git checkout -b development main && git push -u origin development
fi

# Garante branch protection (idempotente — falha silenciosamente se já configurado)
bash .claude/scripts/ensure-development-branch.sh || true

exit 0
```

## 8. Script: `open-task-pr.sh`

```bash
#!/usr/bin/env bash
set -euo pipefail

WORKTREE_PATH="$1"
TASK_DESCRIPTION="$2"
COMMIT_MSG="$3"

cd "$WORKTREE_PATH"

BRANCH=$(git rev-parse --abbrev-ref HEAD)

# Stage e commit
git add -A
if git diff --staged --quiet; then
  echo "No changes to commit"; exit 1
fi

git commit -m "$COMMIT_MSG"
git push -u origin "$BRANCH"

# Captura nome do primeiro arquivo do commit pra body
FILES=$(git diff --name-only origin/development...HEAD)

TITLE=$(echo "$COMMIT_MSG" | head -1)

BODY=$(cat <<EOF
## Task
$TASK_DESCRIPTION

## Files changed
\`\`\`
$FILES
\`\`\`

## Local gate
- pytest: passed
- ruff check: passed
- ruff format: passed

Generated by VisionForge agent team.
EOF
)

PR_URL=$(gh pr create --base development --draft --title "$TITLE" --body "$BODY")
echo "$PR_URL"
```

## 9. Script: `wait-for-ci.sh`

```bash
#!/usr/bin/env bash
set -uo pipefail

PR_NUMBER="$1"
TIMEOUT_SECS="${2:-1800}"  # 30 min default

# Tira de draft pra disparar CI completo
gh pr ready "$PR_NUMBER" >/dev/null

# Polling com timeout
SECONDS=0
while [ $SECONDS -lt $TIMEOUT_SECS ]; do
  STATUS=$(gh pr checks "$PR_NUMBER" --json state --jq '[.[].state] | unique')
  case "$STATUS" in
    *FAILURE*|*CANCELLED*|*TIMED_OUT*)
      echo "CI failed"; exit 2 ;;
    *PENDING*|*IN_PROGRESS*|*QUEUED*)
      sleep 30 ;;
    *SUCCESS*)
      if ! echo "$STATUS" | grep -qv SUCCESS; then
        echo "CI passed"; exit 0
      fi
      sleep 30 ;;
    *)
      sleep 30 ;;
  esac
done

echo "Timeout waiting for CI"; exit 3
```

## 10. Script: `merge-when-green.sh`

```bash
#!/usr/bin/env bash
set -euo pipefail

PR_NUMBER="$1"

# Pede review final (handshake via SendMessage feito pelo lead, não pelo script)
# Este script é chamado DEPOIS que o reviewer já aprovou

# Confirma estado
REVIEW_STATE=$(gh pr view "$PR_NUMBER" --json reviewDecision --jq .reviewDecision)
if [ "$REVIEW_STATE" != "APPROVED" ]; then
  echo "PR not approved (state: $REVIEW_STATE)"; exit 2
fi

# Merge (--auto espera CI verde se ainda em andamento)
gh pr merge "$PR_NUMBER" --squash --delete-branch --auto

# Aguarda merge confirmar
sleep 5
STATE=$(gh pr view "$PR_NUMBER" --json state --jq .state)
if [ "$STATE" != "MERGED" ]; then
  echo "Merge failed or pending (state: $STATE)"; exit 3
fi

# Atualiza development local
git checkout development
git pull origin development

echo "PR #$PR_NUMBER merged"
```

## 11. Conflict handling

Quando dois PRs do time tocam o mesmo arquivo:

- O primeiro a chegar no merge ganha (`--auto` espera CI verde, então é ordem temporal)
- O segundo PR pega o erro `not mergeable` → lead chama `gh pr update <n> --rebase` que rebase em `development`
- Se o rebase falha (conflito real), lead:
  - Pega o worktree do PR
  - `git rebase origin/development`
  - Se conflito, manda task pro teammate original: "rebase your branch, resolve conflicts in <files>, re-push"
  - Se 2× falha no rebase, escalation

## 12. Stop conditions adicionais (estende Spec A §12)

- `gh auth status` falha no startup → lead refuse start, mensagem clara pro usuário
- PR fica preso em CI vermelho após 3 retries no mesmo erro → escalation
- Conflito de merge não resolvido após rebase → escalation
- `gh api` rate-limited (GitHub, não Anthropic) → exponential backoff, max 3 tentativas

## 14. Risks

| Risco | Mitigação |
|---|---|
| Reviewer-bot vira rubber stamp | Reviewer roda code review **antes** de `gh pr review --approve` — lead garante o handshake via SendMessage |
| Merge em cascata gera N conflitos em série | Serialização explícita: lead processa 1 merge por vez |
| `gh` token expira no meio do loop | `lead-startup.sh` valida no início; Spec C re-valida em cada ciclo |
| Branch protection rule difere por repo (org settings) | `ensure-development-branch.sh` falha gracioso e loga, não bloqueia |
| PR aberto fica órfão se lead crashar | Spec C lê `gh pr list --state=open` no resume e re-junta o estado |
